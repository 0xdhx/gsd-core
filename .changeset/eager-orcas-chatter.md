**`deferred-items.md` entries written with `*`, `+` or an ordered marker are no longer silently dropped** — the parser recognised only `- `, so a deferred list written with any other standard Markdown list marker contributed zero entries and reported as a clean zero to `audit-open`. Also fixed: a `status:` line inside a fenced code block indented four or more spaces — what a fence under a nested bullet looks like — was not treated as fenced, so a `status: resolved` written as documentation resolved the entry containing it. (#3702, #3740)

**Breaking, and deliberate: a heading-delimited `deferred-items.md` written with one of the newly recognised markers now HALTS `complete-milestone` instead of closing.** Those files previously parsed to zero entries, so the close had nothing to acknowledge and proceeded — reporting success over items that were never suppressed. They now yield entries, and the CLI writer refuses the heading-delimited shape (`unsupported_heading_shape`), which `complete-milestone` accumulates into `ACK_FAILURES` and halts on with `exit 1`. Measured against `next`: `*`, `+` and `1.` heading-shaped files went from `0 entries → close proceeds` to `1 entry → refusal → halt`; the `-` form already halted and is unchanged. If a milestone close starts failing this way, the file is a real backlog of unsuppressed items — edit `deferred-items.md` into the bullet shape, or resolve the entries, rather than reverting to the silent close.
